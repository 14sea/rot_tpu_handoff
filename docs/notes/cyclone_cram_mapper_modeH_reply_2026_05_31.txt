PART B -- XPART REALITY CHECK (the user's actual question)
--------------------------------------------------------------------------------

What XPART is: Xilinx Partial Reconfiguration Toolkit, derived from JBits, built
on ICAP -- a HW-independent C API for runtime fine-grain reconfiguration of
selected CRAM resources (tune LUTs, constant-folding, MGT tuning) WITHOUT a full
reconfig, including self-reconfiguration from inside the chip.

Hardware fact (Intel docs): Cyclone IV E (EP4CE6/CE10) has NO ICAP and does NOT
support partial reconfiguration. Full reconfig is required. (Partial recon starts
at Stratix/Arria.) So the literal XPART property -- live edit with no halt -- is
physically unavailable on this silicon.

What you already built IS the achievable equivalent:
  mode-H = real .rbf LUT-cell surgery via sigma-inv math + frame-CRC repair,
           staged to EPCS slot 1, promoted slot1->slot0, then COLD-BOOT.
  This is "XPART minus live-ness": genuine CRAM/LUT surgery, applied through the
  EPCS-stage + cold-boot path (the Cyclone IV substitute for ICAP).
  Silicon-validated 2026-05-21: 1 LE @ (X22,Y12,N4) 0x0000->0xFFFF, byte-identical
  to host oracle, exactly 1 changed LE, no collateral.
Recommendation to the user: do NOT chase ICAP/live XPART on Cyclone IV. mode-H is
the right design. Frame it as "JBits/XPART-class LUT surgery via EPCS staging +
cold-boot", which is exactly what the README already says.

PART C -- WHAT THE PRODUCER MUST ADD TO GENERALIZE XPART (the real gap list)
--------------------------------------------------------------------------------
All producer-side mining (Python + Quartus compiles, NO flash). Ranked by leverage.

Pivotal measurement (2026-05-31): canon cells are PARTLY mask-dependent --
  0x6996 <-> 0xDEAD  jaccard 0.88-0.97  (XOR-class masks share canon)
  0x4444 <-> 0x6996/DEAD  jaccard 0.44-0.57  (partial)
  anything <-> 0xFFFF  jaccard 0.01-0.22  (bypass/const is its own class)
=> canon is neither per-position-invariant nor cleanly per-mask. Generalizing
   needs a mine per (position, MASK-CLASS), not per position and not per raw mask.
   Mask-classes to budget for: XOR-class, AND/OR-perm-class, bypass/const-class.

  1. CANON TABLE COVERAGE. Today: 14 positions x 4 masks. Full XPART ("any LUT")
     wants the full pin-friendly whitelist 4 x 18 x 16 = 1152 (x,y,n) x the
     mask-classes you will actually use. Recipe = scripts/mode_h/build_canon_d1pp_table.py
     + Quartus compiles. Size by mask-CLASS, not all 65536 masks.

  2. ODD-N / FULL-N COVERAGE. Demo used even N. P4 (2026-05-29) proved canon is
     PER-N (not N-invariant) -- each N slot needs its own mine. (Your contract Q3
     explicitly deferred odd-N; this is where it comes back.)

  3. EDITABLE-LE ALLOWLIST (your wanted editable_les.bin sidecar). Producer emits
     a per-base list of LE positions safe to XOR-edit, cross-checked with D3
     FF-avoid -- turns the pin-friendly whitelist into a hard safety gate in lc_init.

  4. BEYOND-LUT SURGERY -- RECOMMEND OUT OF SCOPE. ROUTE/IOB/M9K runtime edits hit
     the context-dependent LI-MUX composition wall that silicon-FAILED twice on the
     producer side (P5d 2026-05-21, Track D 2026-05-28). Real XPART's headline use
     case is LUT tuning / constant folding anyway. Keep XPART = LUT-truth-table-only.

  5. (Optional) A thin Python lut_edit() reference + ctypes parity test in the
     mapper that mirrors your C lut_apply_mask, so we can regression-test your C
     codec against the Python oracle without you shipping golds each time.
